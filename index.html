Android Framework / AOSP — 開發紀錄

一個功能，六層架構，沒有捷徑。

DeviceGuardService 是一個貫穿 Android 系統堆疊的完整垂直切片—— 一個應用層看到的政策功能，一路實作到 SystemServer 註冊的系統服務、 AIDL HAL 邊界，以及真正負責強制執行的 SELinux 政策。 基於 Android 14 開發，於 Cuttlefish 上測試驗證。

00 — 為什麼要做垂直切片

應用層反哺框架層

十年的 Android 應用層開發經驗(Kotlin、MVVM、Jetpack Compose) 回答的是「裝置應該做什麼」。這個專案要補上另一半： 「平台實際上怎麼強制執行」。以下每個 milestone 都往下深入一層—— 從一支可呼叫的 API，到系統服務，再到任何 App 都無法繞過的 HAL 與政策層。

App → Manager SDK → SystemService → AIDL HAL → SELinux Policy → Kernel/Driver
01 — 里程碑

從一個可綁定的服務，到一套政策平台

M1 · SystemService 基礎建設

已完成
@SystemApi Binder SystemServer
  • DeviceGuardService 以 @SystemApi 形式對外開放，開機時直接在 SystemServer 中註冊。
  • 透過 Binder IPC 連接一個輕量的 Manager SDK，供 App 呼叫使用。
  • 正式開發前，先用一個較小的練習專案(HelloService)驗證 SystemService 生命週期、fuzzer binding 註冊、以及 API snapshot 同步機制。

M2 · AIDL HAL + SELinux 雙閘門模型

已完成
AIDL HAL SELinux 權限模型
  • AIDL HAL 邊界將框架層服務與硬體 / 政策執行層分隔開來。
  • 採用雙閘門執行模型：框架層權限檢查 加上 SELinux domain/type 規則——單一層都無法單獨授予存取權限。
除錯筆記——一個 avc: denied 錯誤，追查後發現是把 SELinux 政策裡的 find(查找)權限跟 add(註冊)權限搞混了；這兩者是各自獨立的授權，需要分開設定規則。

M3–M5 · AMS / WMS / PMS 三部曲

進行中
IProcessObserver WindowManager PackageManager PolicyStore
  • M3 — 透過 IProcessObserver 偵測黑名單前景 App(AMS)。
  • M4 — 透過 WindowManager 觸發系統浮層警告(WMS)。
  • M5 — 透過 PackageManager 監控安裝行為(PMS)。
shared PolicyStore ← setBlacklist (AIDL) ← {AMS, WMS, PMS}

設計上是一套共用的 policy store，統一透過單一 setBlacklist AIDL API 存取， 而不是三個各自獨立的 demo——重點在於跨子系統的一致性架構設計，而非三個一次性功能。

02 — 除錯紀錄

真正學到東西的地方

avc: denied { find }

SELinux find 與 add 的差異

服務查找(lookup)與服務註冊(registration)由不同的 SELinux 權限管控——只修好其中一個，另一個情境下仍會重現拒絕存取的錯誤。

UnflaggedApi

新增 SystemApi 介面 vs. lint 檢查

新增一個 @SystemApi 介面會觸發 API flagging lint 檢查，除非該介面被正確宣告與標記，光是實作出來還不夠。

framework.jar

API snapshot 驗證

框架層 API 的變更會對照公開介面的 snapshot 進行檢查——不一致會在編譯階段就失敗，而不是等到執行期才出問題。

04 — 向前看

Android 15 → 16 遷移影響評估

在正式環境出問題之前，就該先讀懂 diff。以下是對本專案各模組的影響分析：

  • PackageManager — dexopt 時機點的變化。
  • WindowManager — 更嚴格的方向性(orientation)強制規則。
  • JobScheduler — 更緊縮的配額，影響背景排程的既有假設。
  • AVF / pKVM — 虛擬化範圍擴大，與未來 HAL 隔離設計相關。
