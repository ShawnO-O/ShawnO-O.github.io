Android Framework / AOSP — 開發紀錄

一個功能，六層架構，沒有捷徑。

DeviceGuardService 是一個貫穿 Android 系統堆疊的完整垂直切片—— 一個應用層看到的政策功能，一路實作到 SystemServer 註冊的系統服務、 AIDL HAL 邊界，以及真正負責強制執行的 SELinux 政策。 基於 Android 14 開發，於 Cuttlefish 上測試驗證。

00 — 為什麼要做垂直切片

應用層反哺框架層

十年的 Android 應用層開發經驗(Kotlin、MVVM、Jetpack Compose) 回答的是「裝置應該做什麼」。這個專案要補上另一半： 「平台實際上怎麼強制執行」。以下每個 milestone 都往下深入一層—— 從一支可呼叫的 API，到系統服務，再到任何 App 都無法繞過的 HAL 與政策層。

App → Manager SDK → SystemService → AIDL HAL → SELinux Policy → Kernel/Driver
01 — 里程碑

從一個可綁定的服務，到一套政策平台

M1 · SystemService 基礎建設

已完成
@SystemApi Binder SystemServer
開發
  • DeviceGuardService 以 @SystemApi 形式對外開放，開機時直接在 SystemServer 中註冊。
  • 透過 Binder IPC 連接一個輕量的 Manager SDK，供 App 呼叫使用。
  • 正式開發前，先用一個較小的練習專案(HelloService)驗證 SystemService 生命週期、fuzzer binding 註冊、以及 API snapshot 同步機制。
驗證

建置後燒錄到 Cuttlefish；確認服務在 SystemServer 開機流程中正確啟動，並確認 Manager SDK 發出的 Binder 呼叫能正確來回。

問題
  • 新增的 @SystemApi 介面觸發了 UnflaggedApi lint 檢查，直到正確宣告與標記後才通過，光是實作出來還不夠。
  • framework.jar 的 API snapshot 驗證抓到與公開介面不一致的地方——這一關會在編譯階段就失敗，不會拖到執行期才出問題。

M2 · AIDL HAL + SELinux 雙閘門模型

已完成
AIDL HAL SELinux 權限模型
開發

AIDL HAL 邊界將框架層服務與硬體 / 政策執行層分隔開來。採用雙閘門執行模型：框架層權限檢查 加上 SELinux domain/type 規則——單一層都無法單獨授予存取權限。

驗證

在 Cuttlefish 上分別測試兩道閘門——確認光靠框架層權限檢查不夠，必須搭配對應的 SELinux 規則；反之亦然。

問題

一個 avc: denied { find } 錯誤，追查後發現是把 SELinux 政策裡的 find(查找)權限跟 add(註冊)權限搞混了——這兩者是各自獨立的授權，需要分開設定規則。

M3 · AMS 黑名單偵測

進行中
IProcessObserver PolicyStore
開發(規劃中)

透過 IProcessObserver 偵測黑名單前景 App，並將結果送入共用的 PolicyStore，而非在本地各自處理。

驗證(規劃中)

在 Cuttlefish 上確認前景切換偵測的可靠性，同時不會對 ActivityManager 的 observer callback 造成明顯額外負擔。

待解風險

大規模情境下 IProcessObserver 的呼叫頻率是目前最大的未知數。

M4 · WMS 浮層警告

進行中
WindowManager PolicyStore
開發(規劃中)

當共用 PolicyStore 標記出前景違規時，透過 WindowManager 觸發系統浮層警告。

驗證(規劃中)

確認浮層遵守既有的視窗 z-order 與 focus 規則，不會擋住下層合法的系統 UI。

待解風險

浮層渲染權限與其他正在運作中的系統浮層之間的 z-order 衝突。

M5 · PMS 安裝監控

進行中
PackageManager PolicyStore
開發(規劃中)

透過 PackageManager callback 監控安裝行為，並比對 M3、M4 共用的同一份黑名單。

驗證(規劃中)

在 Cuttlefish 上驗證安裝時偵測的延遲與誤判率，比對共用的 PolicyStore。

待解風險

安裝時檢查要夠快，才不會讓一般套件安裝出現明顯延遲。

shared PolicyStore ← setBlacklist (AIDL) ← {AMS, WMS, PMS}

M3–M5 設計上是一套共用的 policy store，統一透過單一 setBlacklist AIDL API 存取， 而不是三個各自獨立的 demo——重點在於跨子系統的一致性架構設計，而非三個一次性功能。

02 — 建置環境

03 — 向前看

Android 15 → 16 遷移影響評估

在正式環境出問題之前，就該先讀懂 diff。以下是對本專案各模組的影響分析：

  • PackageManager — dexopt 時機點的變化。
  • WindowManager — 更嚴格的方向性(orientation)強制規則。
  • JobScheduler — 更緊縮的配額，影響背景排程的既有假設。
  • AVF / pKVM — 虛擬化範圍擴大，與未來 HAL 隔離設計相關。
